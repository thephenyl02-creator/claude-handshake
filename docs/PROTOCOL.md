# claude-handshake — handshake protocol v1

**Status: FROZEN (M1, 2026-08-15). Protocol version integer: `1`.**

This document is normative. It defines the wire format, semantics and budgets
that every claude-handshake client, relay and transport adapter MUST implement
to interoperate. Nothing in it is aspirational: features that do not exist in
v1 appear only in [Deferred beyond v1](#deferred-beyond-v1).

The key words MUST, MUST NOT, REQUIRED, SHALL, SHOULD, SHOULD NOT, MAY are to
be interpreted as in RFC 2119/8174.

**Source tags.** Every fixed number and rule carries its origin:

| Tag | Meaning |
|---|---|
| `[D#]` | decision # in `docs/M1-decisions.md` ("The twelve") |
| `[R#]` | relay decision # ratified in `docs/M1-decisions.md` (numbering from `docs/M1-open-questions.md` §"Relay decisions to ratify") |
| `[S#]` | frozen fact # in `docs/spike-findings.md` |
| `[P§n]` | `PLAN.md` section n |
| `[C]` | value as implemented in the relay source (file named inline) |
| `[F]` | first frozen here at M1; no earlier source |

`docs/M1-decisions.md`, `docs/M1-open-questions.md` and `docs/spike-findings.md`
are development history kept in the source repo; they are NOT included in the
plugin zip (`scripts/build-plugin-zip.js` ships only `docs/PROTOCOL.md`,
`docs/SECURITY.md` and `docs/INSTALL.md` out of `docs/`). A
reader of the shipped artifact who cannot resolve a `[D#]`/`[R#]`/`[S#]` tag

`[D preamble]`. Where the relay source and the decisions disagree, the
decisions win and the difference is recorded in
[Appendix B — Implementation deltas](#appendix-b--implementation-deltas).

## 1. Identifiers and terminology

| Term | Definition | Format |
|---|---|---|
| **workspace** | one collaborating group on one project | — |
| `ws` | workspace id | 32 lowercase hex chars = 128-bit CSPRNG `[C relay/src/lib/tokens.js]`. On the team relay it is minted **server-side only** `[P§3]`; on ntfy it is minted locally by `init` `[F]`. |
| **workspace secret** | the shared key material all members hold; the *only* input to signing and body encryption | 32 bytes CSPRNG, transported as base64url (43 chars) `[F]` |
| **member name** | the human-facing handle chosen at join; unique per workspace; permanently retired on removal | printable ASCII, 1–64 chars after trim, regex `^[\x20-\x7e]{1,64}$` `[C relay/src/do/workspace.js]`, charset per `[D8]` |
| `member` (member id) | the value carried in `from.member`; the authoritative machine handle | Relay: the relay-issued id, 16 lowercase hex `[C tokens.js]`. ntfy: the self-assigned member name (no server exists to mint one) `[F]`. |
| `display_name` | OPTIONAL human label; never authoritative | UTF-8, sanitized, ≤ 40 chars `[D8]` |
| `machine` | per-install pseudonym, **never** a hostname `[P§2]` | `m-` + 8 lowercase hex `[F]`; ≤ 64 chars `[C]` |
| `session` | per-session opaque handle | `s-` + first 16 hex of SHA-256 of the host session id `[F]`; ≤ 64 chars `[C]` |
| **member sub-token** | per-member bearer credential minted at join | `hsm_<16 hex member id>_<64 hex secret>` `[C tokens.js]` |
| **enrollment token** | workspace join credential (relay only) | `hsk_<64 hex>_<8 hex checksum>` `[C tokens.js]` |
| **recovery key** | admin credential (relay only) | `hsr_<64 hex>_<8 hex checksum>` `[C tokens.js]` |

**Naming reconciliation.** `[D8]` says "member id charset stays printable
ASCII". The relay separates an opaque `member_id` (hex) from the printable
`name`. Both are kept: the printable-ASCII rule binds the **member name** and
any self-assigned ntfy member id — i.e. every identifier that can reach a
peer's model context. Relay-minted hex ids are a strict subset of printable
ASCII and satisfy the rule trivially.

**Key separation (frozen).** The workspace secret is NOT the enrollment token.
`[P§2]` says "the workspace secret is demoted to an enrollment credential";
that describes its loss of *authority*, not an identity of key material. They
MUST be distinct values because:

- the relay mints and stores the enrollment token, and rotation `[R5]` replaces
  it — signatures MUST survive an offboarding rotation;
- the relay never holds the workspace secret and MUST NOT be able to forge or
  read signed traffic `[C: relay never verifies `sig`]`;
- the ntfy transport has no enrollment token at all, yet still signs.

Therefore: **the workspace secret is client-side key material only.** It is
generated by `init`, distributed with the invite / private repo, and used
exclusively as HKDF input material (§2.3, §2.4). It MUST NOT be sent to any
relay, and MUST NOT be used directly as an HMAC key.

## 2. Envelope

### 2.1 Fields

Every message on every transport is one envelope.

| Field | Type | Req. | Rule |
|---|---|---|---|
| `v` | integer | MUST | `1` for this protocol `[C envelope.js]` |
| `ws` | string | MUST | the workspace id, §1 |
| `from` | object | MUST | `{member, machine, session}`, all strings, all REQUIRED `[D3]` |
| `type` | string | MUST | event type, §3; regex `^[a-z][a-z0-9]{0,15}\.[a-z][a-z0-9_]{0,31}$` `[C envelope.js]` |
| `body` | object | MUST | per-type schema, §3; ≤ 2048 bytes UTF-8 when serialized `[C envelope.js]` `[P§2]` |
| `ts` | integer | MUST | **Unix milliseconds** `[D1]` |
| `nonce` | string | MUST | CSPRNG, 16 bytes as base64url unpadded (22 chars) `[F]`; regex `^[A-Za-z0-9_-]{8,128}$` `[C envelope.js]` |
| `sender_seq` | integer | MUST | per-sender dedupe counter, §2.6 `[D2]` |
| `sig` | string | MUST | 64 lowercase hex chars = HMAC-SHA256, §2.3 `[F]` |
| `alg` | string | MAY | signature algorithm; absent means `"HS256"`. `"HS256"` is the only value in v1 `[F]`, field reserved by `[P§2]` |
| `enc` | string | conditional | body-encryption algorithm; MUST be `"A256GCM"` on ntfy (§9.3) and MUST be absent on the relay `[F]`, field reserved by `[P§2]` |
| `ct` | string | conditional | base64url ciphertext; present iff `enc` is present (§9.3) `[F]` |

Rules:

- A receiver MUST reject an envelope with `v` ≠ 1 (§11 governs the response).
- A receiver MUST ignore any top-level field not listed above. Unknown fields
  are **outside the signature** (§2.2) and therefore unauthenticated; acting on
  one would be acting on unsigned data.
- All object keys in the envelope and in `body` MUST match `^[a-z][a-z0-9_]*$`
  `[F]`. This makes code-unit ordering and code-point ordering identical, so
  §2.2 is unambiguous across languages.
- All numbers in the envelope and in `body` MUST be integers `[F]`. Floating
  point is forbidden because its shortest-round-trip serialization is not
  portable enough to sign.
- Total serialized envelope ≤ 8192 bytes `[C envelope.js]`.

### 2.2 Canonical serialization (byte-precise)

The **canonical serialization** of an envelope is a UTF-8 byte string produced
as follows `[D3]`:

1. Take exactly these eight fields, and no others:
   `{v, ws, from, type, body, ts, nonce, sender_seq}`.
   `sig`, `alg`, `enc`, `ct` and any unknown field are excluded.
2. Emit JSON (RFC 8259) with **no whitespace whatsoever**: no spaces, no
   newlines, no indentation, nothing between tokens.
3. In every object — top level and recursively inside `from` and `body` — emit
   keys sorted **ascending by Unicode code point**. Because §2.1 restricts keys
   to `[a-z0-9_]`, this equals byte-ascending ASCII order.
4. Arrays keep their given order; array order is semantically significant.
5. Omit keys whose value is absent/undefined. An explicit `null` is emitted as
   `null` and is a distinct value from absence.
6. Integers are emitted in shortest decimal form, no leading `+`, no leading
   zeros, no exponent, no fraction. `-0` MUST NOT appear.
7. Strings are emitted as JSON strings escaping exactly and only: `"`, `\`, and
   U+0000–U+001F (using `\b \f \n \r \t` where defined, `\u00XX` lowercase-hex
   otherwise). All other characters — including `/`, U+007F, and every
   non-ASCII character — are emitted literally as UTF-8. Lone surrogates MUST
   NOT appear.

The resulting byte string is the HMAC input. It is never transmitted; both
sides recompute it.

For the top eight fields the sorted key order is fixed and is always:

```
body, from, nonce, sender_seq, ts, type, v, ws
```

### 2.3 Signing

```
K_sig = HKDF-SHA256(
          IKM  = workspace_secret (32 raw bytes),
          salt = ASCII bytes of the workspace id `ws` (32 bytes),
          info = UTF-8 "claude-handshake/v1 sig",
          L    = 32 )                                              [F]

sig   = lowercase hex( HMAC-SHA256( K_sig, canonical_serialization ) )
```

- Senders MUST sign every envelope on every transport `[P§2]`.
- Receivers MUST verify `sig` before any other interpretation, using a
  constant-time comparison, and MUST discard the message on failure `[P§2]`.
  A verification failure is a **loud** condition (§10).
- The workspace secret MUST NOT be used directly as the HMAC key; the HKDF step
  with a distinct `info` provides domain separation from §2.4 `[F]`.
- The relay does NOT verify `sig` — the HMAC is end-to-end between clients
  `[C relay/src/lib/envelope.js]`. Clients MUST NOT treat relay acceptance as
  authentication.

### 2.4 Body encryption (transport-conditional)

Applied on the ntfy zero-setup transport only (§9.3); MUST NOT be used on the
relay in v1.

```
K_enc = HKDF-SHA256( IKM=workspace_secret, salt=ASCII(ws),
                     info="claude-handshake/v1 body", L=32 )        [F]
```

### 2.5 Validity limits

| Limit | Value | Source |
|---|---|---|
| `ts` freshness window | ±300000 ms (±5 min) | `[C envelope.js]` `[P§2]` |
| body | ≤ 2048 bytes | `[C envelope.js]` |
| envelope | ≤ 8192 bytes | `[C envelope.js]` |
| relay HTTP request body | ≤ 16384 bytes | `[C relay/src/worker.js]` |
| claim subject | ≤ 200 chars | `[C relay/src/lib/subject.js]` |
| presence `note` | ≤ 280 chars | `[C workspace.js]` |
| `branch` | ≤ 200 chars | `[C workspace.js]` |
| `machine`, `session` | ≤ 64 chars each | `[C workspace.js]` |
| file path entry | ≤ 300 chars | `[C workspace.js]` |
| files per claim | ≤ 64 | `[C config.js MAX_FILES_PER_CLAIM]` |
| members per workspace | ≤ 200 | `[C config.js MAX_MEMBERS]` |
| live claims per workspace | ≤ 500 | `[C config.js MAX_CLAIMS]` |

A receiver MUST reject an envelope whose `ts` is outside the freshness window,
and MUST reject an envelope whose `ws` does not equal the workspace it is
reading (§ Appendix B, delta A5).

### 2.6 Dedupe, ordering, replay

- `sender_seq` is **strictly increasing per member** `[D2]` `[P§2]`. It exists
  for dedupe only; cross-sender ordering comes from the transport handle
  (relay `seq`, ntfy `message_id`) `[P§2]`.
- An implementation MUST persist `sender_seq` in local state. When no counter
  exists (fresh install, restored machine, post-rebind), it MUST be initialized
  to the current Unix ms `[F]` — this guarantees forward progress after local
  state loss without a server round trip, and prevents a reused pair from being
  silently swallowed as a duplicate.
- Receivers MUST discard an envelope whose `(from.member, sender_seq)` pair was
  already accepted. The relay enforces the same pair with a unique index and
  answers a repeat idempotently with the original
  `{seq, received_at, duplicate:true}` `[C workspace.js]` — this is what makes
  offline-queue replay safe (§10.3).
- `nonce` exists so that two envelopes identical in every other field still
  differ, and so a replay inside the freshness window is detectable. Receivers
  SHOULD keep seen nonces for the length of the freshness window.
- Envelopes are not ordered across senders. No client behavior may depend on
  cross-sender ordering.

## 3. Event type catalog

The catalog is **closed for v1 senders**: a v1 client MUST NOT originate a type
outside this table `[F]`. Receivers MUST ignore unknown types silently (count
them; do not error) so a v2 peer degrades rather than breaks (§11). The relay
accepts any type matching the type regex on purpose — forward compatibility
lives at the transport, semantics live at the client
`[C relay/src/lib/envelope.js]`.

| Type | Meaning |
|---|---|
| `presence.update` | this member's liveness and current focus |
| `task.claim` | claim (or re-claim/renew) a subject |
| `task.release` | give up a claim |
| `task.done` | work on a claimed subject finished |
| `task.change` | material change to an existing claim |
| `note.discovery` | something learned that peers should know |
| `note.error` | a failure others may hit |
| `note.fix` | how an error was resolved |
| `note.blocker` | work is blocked; **priority type** (§6) |
| `note.info` | everything else worth saying |
| `warn.overlap` | this member believes two claims collide; **priority type** |
| `ws.join` | a member joined the workspace |
| `ws.leave` | a member is signing off |
| `ws.migrate` | the workspace is moving transport (§9.4) |
| `state.request` | ask live peers to re-announce claims/presence |

Priority types are exactly `warn.*` and `note.blocker`
`[C relay/src/lib/envelope.js isPriorityType]`.

### 3.1 Carriage per transport (frozen)

The relay holds presence and claims as **server state** behind dedicated
endpoints; ntfy has no server, so the same information travels as envelopes.
Which is used is not a client choice `[F]`:

| Type | Team relay | ntfy |
|---|---|---|
| `presence.update` | `POST /ws/:id/heartbeat` — **not** an envelope | envelope on `<topic>-p` |
| `task.claim`, `task.release` | `POST /ws/:id/claim`, `POST /ws/:id/release` — **not** envelopes | envelope on `<topic>` |
| `task.done`, `task.change` | envelope via `POST /ws/:id/post`, **plus** the matching `release`/`claim` call that changes server state | envelope on `<topic>` |
| `note.*`, `warn.*`, `ws.join`, `ws.leave`, `ws.migrate` | envelope via `POST /ws/:id/post` | envelope on `<topic>` |
| `state.request` | MUST NOT be sent — `GET /ws/:id/sync` already returns full state | envelope on `<topic>` |

On the relay a client MUST NOT also post `presence.update`, `task.claim` or
`task.release` as envelopes: it would create unauthenticated shadow state
alongside the server's, and burn the message budget of §9.2 on data every
`sync` already returns. Relay readers learn about new and released claims by
diffing `sync.claims[]` against their cache, and about presence from
`sync.presence[]`.

The body schemas below define the payload in both cases; on the relay the named
endpoint's request body carries the same fields, minus those the server derives
(`acquired_at`, `subject_key`, and everything in `from`).

### 3.2 Body schemas

Shared conventions: `subject` is the raw claim subject; `subject_key` is its
normalization (§5.1) and MUST be present whenever `subject` is, so a receiver
never has to re-derive it to match. All `at`/`_at` fields are Unix ms `[D1]`.
Every string field is subject to the outbound secret filter and the inbound
escaping rules (SECURITY.md §5).

**`presence.update`**

| Field | Type | Req. | Rule |
|---|---|---|---|
| `state` | string | MUST | `working` \| `waiting` \| `blocked` \| `tooling_broken` `[D9]` |
| `note` | string | MAY | ≤ 280 chars; what the member is doing, in the member's own words |
| `branch` | string | MAY | ≤ 200 chars |
| `agents` | integer | MAY | ≥ 0; count of active child sessions aggregated into this member (§7) |
| `tooling` | object | conditional | REQUIRED iff `state == "tooling_broken"`: `{reason}` , `reason` ≤ 120 chars `[F]` |
| `claims` | array | conditional | REQUIRED on ntfy (§9.3 resurrection), MUST be absent on the relay `[F]`. Entries `{subject, subject_key, acquired_at, ttl}`, `subject` ≤ 120 chars, ordered by `acquired_at` ascending |
| `claims_truncated` | boolean | MAY | `true` when `claims` was trimmed to fit the 2048-byte body cap; trim oldest-`renewed_at` first `[F]` |

`state` MUST NOT include an idle value: no hook ever asserts idle; readers
derive quiet/stale from `updated_at` (§4) `[P§1]`.

**`task.claim`**

| Field | Type | Req. | Rule |
|---|---|---|---|
| `subject` | string | MUST | ≤ 200 chars, semantic free text (§5) |
| `subject_key` | string | MUST | normalization of `subject` (§5.1) |
| `ttl` | integer | MUST | seconds, 1 … 86400; default 7200 `[C config.js]` |
| `acquired_at` | integer | MUST | when this member first acquired the subject — the tiebreak input (§5.3) |
| `files` | array | MAY | ≤ 64 entries, each ≤ 300 chars, repo-relative POSIX paths |
| `renew` | boolean | MAY | `true` when this is a renewal of a claim the sender already holds |

**`task.release`** — `{subject, subject_key, reason}` where `reason` ∈
`done | superseded | tiebreak_loss | manual | expired` `[F]`.

**`task.done`** — `{subject, subject_key, summary, files}`; `summary` ≤ 280
chars; `files` as above.

**`task.change`** — `{subject, subject_key, change, files_added?, ttl?, note?}`
where `change` ∈ `files | ttl | tiebreak_loss | scope` `[F]`; `note` ≤ 280.
A tiebreak loser MUST post `task.change` with `change:"tiebreak_loss"` before
its `task.release` (§5.3) `[P§2]`.

**`note.*`** — `{text, paths?, subject?, subject_key?}`.
`text` ≤ 800 chars `[F]` (the 2048-byte body cap is the hard limit; 800 keeps a
note injectable inside the 5-item / ~600-char inject budget of §6.2).
`paths` ≤ 8 entries × ≤ 300 chars. `subject` links the note to a claim.

**`warn.overlap`** — `{subject, subject_key, peer_member, peer_subject,
peer_subject_key, jaccard, paths?}`. `jaccard` is an integer **percentage**
0–100 `[F]` (integers only, §2.1); the emitter MUST NOT send below 50 (§5.2).

**`ws.join`** — `{member_name, display_name?, protocol, client, transport}`;
`protocol` = 1; `client` = client name/version ≤ 40 chars.

**`ws.leave`** — `{reason, summary?, open_claims?}` with `reason` ∈
`session_end | signoff | error` `[F]`; `summary` ≤ 280 chars; `open_claims` an
array of `subject_key`. This is the parting note `[P§1]`; it MUST also be
written to the local task shard so the record exists in both the live and
durable layers `[P§1]`.

**`ws.migrate`** — `{from_transport, to_transport, endpoint, ws_new, name,
dual_read_until, member_map?}` (§9.4). `member_map` is the object
`{from, to}` — the signed sender's old and new member ids (an id-keyed map
would violate §2.1's key regex and be uncanonicalizable); a client MUST NOT
accept a `member_map` for any member other than the signed sender `[F]`.

**`state.request`** — `{want}` where `want` is a non-empty array over
`claims | presence` `[F]`.

Response duty: a member that verifies a `state.request` MUST answer with a
`presence.update` (carrying `claims` on ntfy) at the earlier of its next turn
boundary or its next heartbeat, and MUST NOT answer more than once per 60 s
regardless of how many requests arrive `[F]` — otherwise a rejoining peer
triggers a broadcast storm inside the ntfy publish budget (§9.3).

## 4. Presence

### 4.1 Records

A presence record is the last `presence.update` from a member, plus the
transport's own receipt time. The relay materializes it as
`{member_id, name, state, note, branch, machine, session, updated_at}`
`[C workspace.js]`. `updated_at` is **server/receiver time**, not sender `ts`;
a sender cannot make itself look fresher than its last delivered message.

### 4.2 Frozen state enum

`working | waiting | blocked | tooling_broken` `[D9]`. No other value is valid;
a receiver MUST reject an out-of-enum state (the relay answers
`400 presence_state_invalid` `[C workspace.js]`).

- `working` — actively producing changes.
- `waiting` — waiting on a human, a peer, or a long external operation.
- `blocked` — cannot proceed; SHOULD be accompanied by a `note.blocker`.
- `tooling_broken` — the plugin is running but a required local dependency is
  unusable (e.g. `node` missing for the CLI path) `[P§1]`. This state exists to
  separate "broken" from "offline"; when nothing can run at all the member
  simply goes stale (§4.3), which is the honest signal.

### 4.3 Reader-derived staleness (never transmitted)

No hook asserts idle `[P§1]`. Every reader derives a label from
`age = now − updated_at` and the transport's keepalive interval `K`
(relay `K` = 60 s, ntfy `K` = 600 s `[D budgets]`):

| Label | Condition | Relay | ntfy |
|---|---|---|---|
| `live` | age ≤ 2.5 × K | ≤ 150 s | ≤ 1500 s |
| `quiet` | 2.5 × K < age ≤ 6 × K | ≤ 360 s | ≤ 3600 s |
| `stale` | age > 6 × K | > 360 s | > 3600 s |
| `gone` | age > 7200 s (the default claim TTL) | | |

Multipliers frozen at M1 `[F]`, sized from the measured monitor tick of
60.0 s ± 20 ms `[S5]`: 2.5 × K tolerates two missed keepalives plus jitter,
6 × K tolerates five. A `gone` member MUST NOT be shown as present, but remains
a member of the workspace until removed (§9.2).

Labels are reader-side only. A client MUST NOT put them in an envelope.

## 5. Claims

Claims are **advisory leases** `[P§2]`. Holding one never grants exclusive
access to anything and never blocks a peer's write; it is coordination, not
locking. Tasks are created implicitly by the first claim; `.handshake/tasks/`
is a projection of claims and is never a hand-edited master `[P§2]`.

Subjects are **semantic-first**: model-authored free text captured at prompt
time ("onboarding flow"), not a file glob `[P§2]`. `files[]` is appended
progressively as work touches paths, and on renewal is a **capped union, never
a replace** `[D12]` (cap 64 `[C config.js]`).

### 5.1 Subject normalization (frozen, byte-identical client and relay)

Frozen exactly as implemented in `relay/src/lib/subject.js` `[D6]`. In prose,
`normalize(subject)`:

1. Coerce to string; reject if longer than 200 chars.
2. Lowercase with the default (non-locale) case mapping. **This happens before
   step 3** — the order is part of the freeze.
3. Apply Unicode normalization form **NFKD**.
4. Delete every character in Unicode general category `M` (combining marks).
   They are deleted, not replaced by a separator, so "café" yields the single
   token `cafe`.
5. Replace every maximal run of characters outside `[a-z0-9]` with a single
   space (this is what folds punctuation, `_`, `-`, and every non-ASCII
   character that survived step 4).
6. Trim leading/trailing spaces and split on runs of whitespace; drop empties.
   Call the result the **raw tokens**, order preserved.
7. Remove tokens present in the frozen stopword list (27 entries, exactly):
   `a an and are as at be but by for from in into is it its my of on or our
   that the their this to with`.
8. If step 7 left at least one token, the **kept tokens** are the result;
   otherwise fall back to the raw tokens (so a subject made only of stopwords
   does not normalize to the empty key that every such claim would collide on).
9. Join with a single space (U+0020). The result is the `subject_key`.

No stemming, no token reordering, no synonym folding — each would merge
genuinely different subjects, and a false merge refuses a peer a claim it
should have won `[C subject.js]`.

Reference results (verified against the implementation):

| input | `subject_key` |
|---|---|
| `Fix the API issue` | `fix api issue` |
| `fix API issue` | `fix api issue` |
| `Onboarding-Flow` | `onboarding flow` |
| `Refactor the Café Menu!` | `refactor cafe menu` |
| `the and of` | `the and of` |

An empty `subject_key` is invalid (`400 claim_subject_invalid`).

### 5.2 Overlap rule (Jaccard ≥ 0.5)

Two subjects **collide** when their `subject_key`s are equal — that is the
one-winner key, and the only thing a transport ever decides.

Two subjects are an **overlap candidate** when their token sets (the
whitespace-split `subject_key`s, as sets — duplicates collapse, order ignored)
have Jaccard similarity `|A ∩ B| / |A ∪ B| ≥ 0.5` `[D6]`.

- Above the threshold the **model** judges whether the work genuinely overlaps
  and MAY emit `warn.overlap`. Below it, no warning is emitted.
- **The transport never judges semantics** `[D6]`. Neither the relay nor the
  ntfy adapter computes or acts on Jaccard.
- `warn.overlap.jaccard` is reported as `round(100 × J)`, and MUST be ≥ 50.

Reference values: `fix api issue` vs `fix api response shape` = 0.40 (no
candidate); `onboarding flow` vs `onboarding flow copy` = 0.67 (candidate);
`refactor auth middleware` vs `refactor auth` = 0.67 (candidate);
`onboarding flow` vs `billing webhooks` = 0.00.

The PreToolUse path gate is separate and is a **path** comparison, not a
subject one: the target `file_path` is matched against peers' cached claim
`files[]` and claim globs before the write `[P§1]` `[S3]`. It MUST warn; it MAY
block only when the workspace config sets `overlap_gate: "block"`; the default
is `warn` `[F]`.

### 5.3 Lifecycle, TTL, renewal

| Property | Value | Source |
|---|---|---|
| default TTL | 7200 s (2 h) | `[C config.js]` `[P§2]` |
| max TTL | 86400 s | `[C config.js]` |
| expiry test | `renewed_at + ttl×1000 ≤ now` | `[C workspace.js]` |
| renewal | the heartbeat tick sets `renewed_at = now` for every claim the member owns, unless the heartbeat carries `renew_claims: false` | `[C workspace.js]` |
| `files[]` on renewal | capped union with the stored list | `[D12]` |

A claim is removed by explicit release, by expiry, or by member removal (which
releases every claim that member held) `[C workspace.js]`.

Restart recovery: on SessionStart a client MUST reconcile local claim state
against the transport and re-adopt its own still-live claims rather than
re-claiming them as new `[P§5 M5]`; re-adoption MUST preserve the original
`acquired_at`, because that value is the tiebreak input.

### 5.4 Deterministic tiebreak

When two members believe they hold the same `subject_key`:

1. The claim with the **earliest `acquired_at`** wins `[P§2]`.
2. If `acquired_at` is equal, the **lexicographically smallest member id** wins
   `[P§2]` — compared byte-wise over the UTF-8 encoding of `from.member` `[F]`.

The rule is evaluated identically by every participant; it never depends on
message arrival order, on politeness between models, or on who asked first
`[P§7]`.

**Loser behavior (MUST, in this order):**

1. Post `task.change` with `change: "tiebreak_loss"`.
2. Post `task.release` with `reason: "tiebreak_loss"`.
3. Stop work on that subject and tell its own user in **one line** — this is
   the one moment surfacing to the human is correct `[P§2]`.

On the relay the Durable Object serializes requests, so exactly one caller wins
a subject at the source and a loser is refused with `409 claim_conflict`
carrying the live claim `[C workspace.js]`. The tiebreak above still governs:
it resolves reconciliation after a partition, after a migration re-broadcast,
and every conflict on ntfy, where no serializing authority exists.

### 5.5 Advisory semantics on unauthenticated transports

On ntfy, claims are marked **unauthenticated-advisory** `[P§2]`: any holder of
the workspace secret can sign as anyone (SECURITY.md §2). Clients MUST label
them as advisory in status output, MUST surface advisory conflicts to the human
rather than silently deferring `[P§2]`, and MUST NOT present a claim as proof
that a peer is or is not editing anything.

## 6. Sync, injection and cursors

### 6.1 Fetch

Per sync round, from the transport:

| Bound | Value | Source |
|---|---|---|
| fetch cap | 20 messages | `[C config.js SYNC_FETCH_CAP]` `[P§2]` |
| reserved priority slots | 5 of the 20 | `[D10]` `[C config.js]` |
| candidate scan window | 200 messages | `[C config.js SYNC_CANDIDATE_WINDOW]` |

Selection is **per-sender-fair round-robin** with the reserved floor filled
first, so one chatty peer cannot bury a quiet peer's `warn.overlap` or
`note.blocker` `[C relay/src/lib/fairness.js]`. Sender order within a round is
by each sender's oldest pending message id — deterministic, never Map insertion
order. A second bounded read pulls priority messages that fell outside the
candidate window, so the reserved floor is real rather than nominal
`[C workspace.js]`. Any transport adapter MUST reproduce this selection when
the transport itself does not (ntfy: the client performs it locally).

### 6.2 Injection

| Bound | Value | Source |
|---|---|---|
| inject cap | 5 items | `[P§2]` |
| standing block budget | ~600 chars | `[P§1]` `[P§2]` |
| overflow | one line: `+N more — /handshake status` | `[P§2]` |

The fetch cap and the inject cap are deliberately different numbers `[P§2]`.
UserPromptSubmit ALWAYS injects the standing block (peer roster + live claims +
standing rules), plus the new-items digest when one is pending `[P§1]`.

### 6.3 Consumed watermark

The watermark advances **at injection time**, not at fetch time `[P§2]` `[R4]`.
Advancing it suppresses re-injection and duplicate reactions. Consequences:

- Reading MUST NOT move the stored cursor. On the relay this is why
  `POST /ws/:id/cursor` is a separate owner-authorized endpoint `[R4]`.
- The cursor moves **forward only**; the relay clamps it with
  `max(requested, stored)` and refuses a value ahead of the highest issued
  message (`400 cursor_ahead_of_stream`) so a client cannot park itself in the
  future and go permanently blind `[C workspace.js]`.

### 6.4 Cursor shape per transport (frozen)

Cursors are transport-specific `[D5]`. A client MUST NOT move a cursor between
transports; a migration resets it (§9.4).

**Relay** — a single non-negative integer, the relay-assigned monotonic message
`seq` `[D2]` `[D5]`. `GET /ws/:id/sync?cursor=N` returns messages with
`seq > N`. The response carries `cursor` (the one used), `next_cursor` (the
highest `seq` actually returned, else `cursor`), `stored_cursor` (the member's
persisted watermark) and `more` (count beyond the cap) `[C workspace.js]`.

**ntfy** — `{message_id, unix_ts}` `[D5]` `[P§2]`. Use:

| Cursor age | Rule | Source |
|---|---|---|
| < 11 h | `since=<message_id>` | `[P§2]` |
| ≥ 11 h, < cache window | `since=<unix_ts>` | `[P§2]` |
| beyond the cache window | **stop pretending**: read the durable layer (`.handshake/` in the repo) and tell the user plainly that older live chatter is gone | `[P§2]` |

The 11 h figure is a deliberate margin under ntfy's ~12 h message cache, which
is operator-controlled and undocumented `[P§2]` `[P§7]`. A client MUST NOT
report a gap as "nothing happened"; a truncated read is a stated fact, not
silence.

## 7. Child mode (subagent and headless sessions)

Plugin hooks fire in **every** subagent/headless session `[S6]` — 21 sessions
in 1.7 h of ordinary research work, each running the full hook set. Untreated,
one six-agent workflow presents as six teammates.

### 7.1 Detection (frozen)

A session is a **child** when `CLAUDE_CODE_CHILD_SESSION=1` is present in the
environment `[D child mode]` (verified live on claude-code 2.1.227 via
claude-desktop). Children also see the parent's id in
`CLAUDE_CODE_SESSION_ID`, which is distinct from the hook payload's own
`sessionId` `[D child mode]`; the parent id is the key under which a child
appends to the parent's claim state (§7.2).

**Safe fallback (MUST):** when the variable is absent, the session is treated as
a child anyway — a session that cannot prove it is a parent behaves as a child —
UNLESS interactive markers are present `[D child mode]`. The interactive
markers recognized in v1 are: a running monitor (monitors start only in
interactive CLI sessions `[S5]`), a SessionStart `source` of
`startup | resume | clear` in an interactive host `[F]`, or an explicitly
human-typed CLI invocation — a typed command is itself an interactive act; the
fallback verdict is still reported in `status`/`doctor` `[F]`. The fallback
fails toward silence, never toward a phantom teammate. Only a *proven* child
(`CLAUDE_CODE_CHILD_SESSION=1`) refuses an explicitly typed posting command.

M6 re-verifies the variable once under terminal-CLI subagents `[D child mode]`;
a change in detection is a client change, not a protocol change — nothing in
this section is on the wire.

### 7.2 The four child rules (frozen)

1. **Never members.** A child MUST NOT join, MUST NOT hold a presence record,
   MUST NOT claim, and MUST NOT post any envelope on any transport.
2. **Honor the gate.** A child MUST run the PreToolUse overlap gate against
   peers' claims, reading the **parent's local cache**. A child performs no
   network I/O for handshake purposes.
3. **Append upward.** A child MUST append its touched files to the parent's
   local claim state, keyed by the parent session id. The parent's next
   heartbeat carries the union (§5.3 capped union), so claims reflect the whole
   agent tree's footprint.
4. **Aggregate, never split.** Presence MAY aggregate child activity into the
   parent's record via `presence.update.agents` (rendered "working: onboarding
   flow (+3 agents)"), and MUST NOT represent a child as a separate member.

Because hook spawn cost multiplies across concurrent agents (218 PostToolUse
spawns observed in 1.7 h `[S6]`), narrow matchers and the mtime-sentinel gate
before interpreter spawn are REQUIRED, not optional (§8).

## 9. Transports

### 9.1 Adapter interface and invite blob (frozen so M3/M4/M5 build in parallel)

Every transport is reached through one adapter `[P§2]`:

```
publish(envelope)            -> {handle}            // handle: relay seq | ntfy message_id
fetch(cursor, limit)         -> {messages[], cursor, more}
presence()                   -> {members[], presence[], claims[]}   // may be derived client-side
commitCursor(cursor)         -> {cursor}
capabilities()               -> {authenticated_from, server_claims, durable_layer,
                                 encrypts_body, keepalive_seconds, cursor_kind}
```

`capabilities()` is what makes the honesty rules of §10.2 mechanical rather
than editorial: `authenticated_from` is false on ntfy and true on the relay;
`server_claims` is false on ntfy (advisory only, §5.5).

**Invite blob** `[P§2]` — a single pasteable token:

```
hsi1_<base64url(canonical JSON, §2.2 rules)>
```

| Key | Type | Meaning |
|---|---|---|
| `p` | integer | protocol version, `1` |
| `t` | string | transport: `relay` \| `ntfy` |
| `e` | string | endpoint: relay origin, or the ntfy base URL |
| `ws` | string | workspace id (32 hex) |
| `n` | string | workspace name, ≤ 64 chars |
| `loc` | string | where the workspace secret lives: `repo` \| `inline` |
| `s` | string | workspace secret, base64url — present **iff** `loc == "inline"` |
| `tok` | string | relay enrollment token (`hsk_…`) — present iff `t == "relay"` and `loc == "inline"` |
| `topic` | string | ntfy topic — present iff `t == "ntfy"` and `loc == "inline"` |
| `c` | string | 8 lowercase hex: first 4 bytes of SHA-256 over the canonical JSON of every key except `c` |

An invite blob is a **credential** whenever `loc == "inline"` (SECURITY.md §3).
`join` MUST print transport, endpoint host and workspace name and require
explicit human confirmation; it MUST NEVER auto-join and MUST NEVER be
triggered by repo content `[P§3]`.

### 9.2 Team relay (Cloudflare Worker + one SQLite Durable Object per workspace)

All JSON. Credentials travel **only** in `Authorization: Bearer <credential>`,
never in a body, so they cannot land in a proxy's request-body log
`[C relay/README.md]`. Every POST body MUST be a JSON object; the envelope
posting shape is `{envelope: {...}}` with room for sibling fields `[D4]`.

**Credential ladder** `[R2]`:

| Credential | Grants |
|---|---|
| `RELAY_CREATE_TOKEN` (deploy secret) | `POST /ws` only. Unset ⇒ `503 relay_not_configured` — fail closed `[R1]` |
| enrollment token `hsk_…` | `POST /ws/:id/join` only |
| member sub-token `hsm_…` | heartbeat, claim, release, post, sync, cursor — always scoped to that member |
| recovery key `hsr_…` | rotate, purge, destroy, member-remove, rebind |

Member-remove sits on the recovery key, not the enrollment token, because on
the enrollment token any member could kick any other `[R2]`.

**Endpoints**

| # | Method / path | Credential | Request | Success | Errors |
|---|---|---|---|---|---|
| 1 | `GET /` | none | — | `200` HTML landing built from frozen constants only | `405`, `429 rate_limited` |

| 3 | `POST /ws` | create token | `{name?}` (≤64) | `201 {ws, name, created_at, enrollment_token, recovery_key}` — **the only time the credentials are ever shown** | `401 invalid_token`, `503 relay_not_configured`, `409 workspace_exists`, `400 body_*`, `429` |

member-remove-by-name fix, first advertised as relay v0.1.3) |

Message wrapper returned by sync: `{seq, from, from_name, received_at,
envelope}`, where the outer `from` is the **authenticated** member id and
`envelope` is stored and returned **verbatim** — every field the client sent,
including `sig` and fields this relay version does not understand `[R3]`
`[C workspace.js]`.

**`from` is refused, never rewritten** `[R3]` `[D3]`: an envelope whose
`from.member` ≠ the authenticated member yields `403 from_mismatch`. Rewriting
would invalidate an end-to-end HMAC the relay cannot recompute. A client MUST
check that the wrapper `from` equals `envelope.from.member` on every message it
accepts `[F]` — that pairing, not the wrapper alone, is what relay attribution
means (SECURITY.md §2).

**Retention**: messages by TTL **and** count — 7 days (`MESSAGE_TTL_SECONDS`
604800) and last 500 (`MESSAGE_MAX`) `[C config.js]` `[P§3]`. Reads filter by
TTL, so an expired message is never returned even before the sweep deletes it.
`next_seq` is never reset by `purge` — reused sequence numbers would move every
cursor backwards and replay old traffic `[C workspace.js]`.

**Rate limiting**

| Bucket | Limit | Scope | Source |
|---|---|---|---|
| auth failures | 10 per 600 s | per IP, inside the workspace object | `[C config.js AUTH_FAIL_MAX / WINDOW]` |
| public (`/`, `/health`) | 120 per 60 s | per IP, limiter DO | `[C config.js PUBLIC_RATE_*]` |
| workspace create | 20 per 3600 s | per IP, limiter DO | `[C config.js CREATE_RATE_*]` |

The auth limit applies to the **failure**, never to the request: a valid
credential is always served even from an IP whose bucket is hot, because NAT
and corporate proxies put whole teams behind one address
`[C workspace.js #denyAuth]`. Guessing a workspace id is deliberately not rate
limited: ids are 128-bit CSPRNG and a workspace object creates its schema only
on `init`, so a guess returns `404` without writing a row `[C workspace.js]`.

**Grace windows**

| Window | Value | Source |
|---|---|---|
| enrollment-token rotation grace | default 86400 s, settable 0–86400 | `[R5]` `[C config.js ROTATE_GRACE_SECONDS]` |
| transport migration dual-read | 86400 s (§9.4) | `[F]` |

Rotation replaces the enrollment token only. It does **not** invalidate
existing member sub-tokens, and it does not rotate the recovery key `[D11]`.

**Workspace binding**: `join` against an uninitialized workspace id is rejected
`404` — there is no first-caller binding, ever `[P§3]` `[C workspace.js]`.
`DELETE` drops the tables, so a destroyed id can never be re-bound
`[C workspace.js]`.

**Observability is off by default** `[R6]`: platform invocation logs record
request URLs, and a URL here contains the workspace id.

### 9.3 ntfy zero-setup transport

Zero setup, zero accounts, **advisory** semantics. This rung exists so a team
can try the product in one paste; every honesty rule below is load-bearing.

**Topic**

- The topic is `≥ 128-bit CSPRNG`, generated at `init`, and **never derived
  from any name** `[P§3]`.
- Encoding: 32 lowercase hex chars `[F]` (ntfy-safe charset).
- The topic is **secret material under the same guard as the token** `[P§3]`,
  and is a bearer credential: possession grants both publish and subscribe
  (SECURITY.md §2).
- Presence rides a **topic suffix**: events on `<topic>`, presence on
  `<topic>-p` `[F]` `[P§2]`. Keepalive traffic therefore cannot dominate the
  event cursor, and a reader that only wants events subscribes to one topic.
  Both topics are equally secret — knowing either yields the other.

**Envelope on the wire (encrypted form)**

The ntfy message body is the JSON object:

```json
{ "v":1, "ws":"…", "ts":1755230000000, "sender_seq":1755229999123,
  "alg":"HS256", "enc":"A256GCM", "sig":"<64 hex>", "ct":"<base64url>" }
```

Only `v`, `ws`, `ts`, `sender_seq`, `sig` (plus the two algorithm labels) are
cleartext `[D/PLAN §2 encryption rule]`. `from`, `type`, `body` and `nonce`
travel inside `ct`. A passive subscriber holding the topic but not the
workspace secret therefore learns no file path, branch, task title, event type
or human name `[P§2]`.

Construction (frozen):

1. `plaintext` = canonical serialization (§2.2 rules) of the four hidden fields
   in sorted order: `{body, from, nonce, type}`.
2. `aad` = canonical serialization of the four cleartext fields in sorted
   order: `{sender_seq, ts, v, ws}`. Binding them as AAD makes header tampering
   fail decryption, not just signature checking.
3. `iv` = 12 CSPRNG bytes, fresh for every message. An IV MUST NOT be reused
   under `K_enc`.
4. `ct` = base64url( `iv` ‖ AES-256-GCM ciphertext ‖ 16-byte tag ), key
   `K_enc` (§2.4).
5. `sig` is computed over the **plaintext** canonical serialization of all
   eight signed fields (§2.2) — i.e. signing is independent of encryption.

Receive order: decrypt (authenticating the AAD) → reassemble the full envelope
→ verify `sig` → apply freshness/dedupe (§2.6). A failure at any step discards
the message.

**Attribution.** There is no server: `from` is explicitly
**self-declared-but-HMAC-signed** `[P§2]`. Any holder of the workspace secret
can sign as any member. Clients MUST NOT claim server-verified identity on this
transport (§10.2, SECURITY.md §2).

**Claims** are `unauthenticated-advisory` (§5.5). Because there is no server
holding state:

- every heartbeat carries the sender's **full active claim set** in
  `presence.update.claims` — this is claim *resurrection* past ntfy's ~12 h
  cache `[P§2]`;
- a new joiner posts `state.request` and waits at most one keepalive interval
  before declaring the roster unknown-but-empty `[F]`;
- the overlap tree surfaces advisory conflicts to the human instead of silently
  deferring `[P§2]`.

**Publish budget**

| Bound | Value | Source |
|---|---|---|
| keepalive | presence on state change + 600 s keepalive | `[D budgets]` `[P§1]` |
| upgrade nudge threshold | ~150 transport operations per day per member, **counting every operation including heartbeats**, or the first `429` | `[P§2]` |
| `429` handling | a loud, user-visible state — never silent degradation | `[P§2]` |
| nudge timing | never mid-conflict; queue it for the next SessionStart | `[P§2]` |

ntfy's public caps are undocumented and operator-controlled; the numbers above
are budgets, not guarantees, and the day-long measurement in M12(b) gates
whether zero-setup remains the default rung `[P§7]`.

**Durable layer.** On a workspace without a GitHub durable layer, status output
MUST say so verbatim in substance: *"zero-setup: claims are advisory; no
durable layer"* `[P§2]`.

### 9.4 Migration (`/handshake upgrade`, zero-setup → relay)

`/handshake upgrade` owns the migration `[P§2]`. Sequence:

1. Script the wrangler deploy; create the workspace; write the new config.
2. Post `ws.migrate` **on the old topic**, naming the new transport, endpoint
   and workspace id, plus `dual_read_until` and the sender's own `member_map`
   entry.
3. Re-broadcast every live claim on the new transport, preserving each claim's
   original `acquired_at` (the tiebreak input, §5.4).
4. **Dual-read** both transports until `dual_read_until`, frozen at 86400 s
   after the migrate post `[F]` — deliberately longer than ntfy's ~12 h cache,
   so a peer that was offline for a normal working day still sees the notice.
   Publish to the new transport only.
5. After the window, stop reading the old topic. A member that never migrated
   MUST be re-invited out of band; the client MUST report which members were
   never seen on the new transport.

Cursors do not migrate (§6.4): the new transport starts at cursor 0 / `null`,
and the client MUST NOT replay pre-migration history into the model.

Identity remap: a member's id changes when moving to the relay (self-assigned
name → relay-minted hex id). A client MUST accept a `member_map` entry only for
the signed sender of that `ws.migrate` `[F]`.

## 10. Failure taxonomy

Two classes, and nothing in between `[P§2]`.

### 10.1 Silent offline (as designed)

Transport unreachable — DNS failure, connection refused, TLS failure, timeout,
5xx, no network. The client MUST NOT interrupt the user. Peers see the member
go `quiet` then `stale` (§4.3), which is the correct and honest signal. This is
also what a hit Cloudflare free-tier daily cliff looks like
`[C relay/README.md]`.

### 10.2 Loud rejected (once per session, and posting stops)

Any of: `401`, `403`, envelope rejection (`400 envelope_*`), signature
verification failure on receive, `from`/wrapper mismatch, `429 rate_limited`,
`404 workspace_not_found`, secret-filter refusal, private-repo guard failure
`[P§2]` `[P§3]`.

Behavior (MUST):

- report once per session, in one line, to that member's own user;
- stop posting on that transport for the rest of the session (a broken
  credential re-tried on a loop is an attack surface and a rate-limit
  amplifier);
- keep reading if reading still works;
- surface state in `/handshake status`: credential state, suppressed-sender
  counts, and the transport tier honestly `[P§2]` — including the zero-setup
  advisory line (§9.3) and "monitors unavailable, heartbeating on turn
  boundaries" where that applies (§8).

Honesty rules for status output (MUST):

- never present an advisory claim as authoritative;
- never present a self-declared `from` as verified;
- never report a truncated read as an empty one;
- state the transport tier and its guarantees, not the aspirational ones.

### 10.3 Offline queue

`[P§2]`, frozen:

| Property | Rule |
|---|---|
| filtering | at **enqueue** and again at **send** |
| file mode | `0600` |
| size cap | 200 envelopes `[F]`, drop-oldest with the dropped count reported |
| `presence.*` expiry | discard once the entry is no longer `live` by §4.3 |
| `task.*` expiry | discard past the claim's TTL |
| `note.*` / `warn.*` expiry | discard after 3600 s |
| `ws.leave` | keep until sent or 86400 s `[F]` |
| hard discard | on any transport, topic, endpoint or token change — reporting the dropped count |

Replay is safe because `(from.member, sender_seq)` is idempotent at the relay
(§2.6). A queued envelope MUST be sent with its original `ts`, and will
therefore be refused by the freshness window if it is older than 5 minutes; a
client MUST re-sign with a current `ts`, a fresh `nonce`, and a **new**
`sender_seq` rather than backdating `[F]`.

## 11. Versioning

- The protocol version is the integer `v` in the envelope, `1` for this
  document. The relay publishes the same integer as `protocol` at `GET /health`
  `[C relay/src/version.js]`.
- A receiver that sees `v > 1` MUST discard the message, count it, and surface
  "a peer is on a newer protocol" once per session (§10.2). It MUST NOT attempt
  partial interpretation.

**A v2 MAY, without breaking a v1 peer beyond that discard:**

- add new event types (v1 receivers ignore unknown types, §3);
- add OPTIONAL envelope or body fields;
- add new transports, endpoints, or capability flags;
- widen an enum, provided v1 values keep their exact meaning;
- change budgets, caps, cadences and thresholds (they are policy, not wire).

**A v2 MUST NOT, without bumping `v`:**

- change the canonical serialization (§2.2) or the signed field set;
- change the signature algorithm, key derivation, or `sig` encoding;
- change subject normalization (§5.1) or the collision key;
- change the claim tiebreak rule (§5.4);
- change the meaning of an existing field, or narrow an enum;
- reuse an existing type name with different semantics;
- make an OPTIONAL field REQUIRED.

Unknown top-level envelope fields are unsigned (§2.1) and MUST be ignored, in
every version. This is what lets a future version add fields without a v1
client ever acting on unauthenticated data.

### B. Tolerated divergences (no patch)

| # | Divergence | Why it stands |
|---|---|---|
| B1 | `normalizeTs()` accepts seconds (`ts < 1e11`) as well as milliseconds. | `[D1]` explicitly keeps the dual-accept "as robustness"; the spec says clients MUST send ms |
| B2 | The relay does not verify `sig`. | By design: the HMAC is end-to-end and the relay never holds the workspace secret (§1, §2.3) |
| B3 | The relay accepts any `type` matching the type regex, not just the §3 catalog — **except** the four §3.1 server-state types (`presence.update`, `task.claim`, `task.release`, `state.request`), which `post` refuses per A6. | Forward compatibility lives at the transport; the closed catalog binds v1 **senders** (§3) |
| B4 | The relay does not track `nonce` replay. | `(sender, sender_seq)` uniqueness plus the ±5 min window bounds replay at the transport; nonce replay detection is a receiver duty (§2.6) |
| B5 | `heartbeat` renews TTL but does not merge `files[]`; the union happens on re-`claim`. | Matches `[D12]` — renewal-union is specified on the claim path, and keeps the heartbeat body small enough for the ntfy budget |
| B6 | `presence` rows accept a client-supplied `machine`/`session`. | They are pseudonyms, not credentials (§1); the authenticated identity is the member id, which the client cannot set |
| B7 | The relay has no notion of the workspace secret. | Required: a relay that held it could forge and read every signed message (§1) |

## Deferred beyond v1

Listed so nothing above is read as a hook for them. None is specified, none is
implemented, none may be assumed by a v1 client.

- **Wake mode** — faster monitor cadence armed by `/handshake watch`; cut from
  v1 entirely, deferred to v1.1 `[P§5 M9]`.
- **Per-member authentication v2** — real per-member keypairs, so `from` is
  cryptographically attributable without a trusted server, and offboarding does
  not require re-keying the workspace.
- **End-to-end encryption on the relay** — `enc`/`ct` on the relay transport,
  so the relay operator sees ciphertext.
- **Display-name widening** — full UTF-8 member identifiers with a targeted
  sanitizer, replacing the printable-ASCII id rule of `[D8]`.
- **Paid hosted tier** — a run-for-you relay, replacing the deploy-your-own
  step `[P Locked decisions 2]`.
